# 音频、麦克风、输入与权限（系统侧）

> 与 [`车机兼容记录.md`](../车机兼容记录.md)（实时 UDP 音频丢包、麦克风被拒、方向盘键）对应，
> 给出**系统侧**的实现位置，说明「为什么应用层改不了」以及有没有官方通道。

## 一、音频扩展 —— `AudioExtService`（`com.autolink.audioextservice`）

包内容（REA 类清单 `evidence/AudioExtService/classes.json`，1237 类）：

**A. Autolink 适配绑定接口** `com.autolink.adapterbinder.*`（37 个 AIDL）：
```
IAudioExtService, IOccAudioService/IOccAudioCallback,
ICarProxyService/ICarProxyCallback, IHardKeyService/IHardKeyCallback,
IDimNaviInteractioncService, IDimMediaInteractioncService, IDimPhoneCallInteractioncService,
IExteriorLightShowCallBack, IOTAService/IOTAServiceCallback, IPower/IPowerCallback,
ISoftApCallback, IWifiApCallback, ITcamService/ITcamActionCallback, ITrackBallInterface,
IUrlInterface, IWebServer, IXCall/IXCallCb, IDIMAppDock,
PsdIBtExtension/PsdBtExtensionListener, PsdGeelyAadpListener, PsdGeelyBtDevice,
PlayMediaInfo, TcamInfo, WifiConfig/WifiInfo, ApInfo/ConDevInfo, TestInfo
```
> `IWifiApCallback` / `ISoftApCallback` / `IWebServer` / `IXCall` / `IPower` 都在这里 ——
> **这是 `adapterservice` 对外暴露的全部车机能力面**（比单个 APP 看到的更全）。

**B. 音频扩展服务** `com.autolink.audioextservice.*`：
```
AudioExtService, AudioExtControlService, IAudioExtControl, AudioInterfaceManager,
FdbusClientInstance, VisualizerManager, SoundEffectsHelper, VehicleFuncManager,
MusicLightShowBean, VoiceLightShowBean, vdb.SomeIPUtils
```
- 含 **FDBus**（`FdbusClientInstance`，软总线）与 **SomeIP**（`vdb.SomeIPUtils`）——音频控制走软总线。
- `VisualizerManager` + `MusicLightShowBean` → **音乐律动氛围灯**。
- `VDSoundAndroidToQnxFocusStatus` / `VDSoundQnxToAndroidFocusStatus`（VDBus `carlan`）：
  **Android 与 QNX（车控域）之间的音频焦点同步**。
- `dy.platform.ComDyIviPlatform`：德赛 IVI 平台 native 桥。

> 与 DiPlay 的关系：CarPlay 音频最终写进 Android 音频栈（`routeType=21` BUS），由 QNX 侧播放。
> 「约 2 秒后 iPhone 停推包」是 Wi-Fi 收包问题（见兼容记录第十节），音频服务侧无解；
> **但** `adaptapi.policy.IAudioPolicy` / `VDSound*FocusStatus` 可用于诊断焦点是否正确切到互联源。

## 二、麦克风

### `OneOSPermissionService`（`com.desaysv.permission.service`，563 类）
- `server.PermissionManagerService`、`PermissionService`、`bean.PermissionGroup`、
  `ui.ShowPermissionDialogActivity` / `AlmostExpirationDialogActivity` / `AlreadyExpirationDialogActivity` /
  `CarLocationExpirationActivity`、`util.PermissionUtils`。
- 对应实测：**麦克风由 secure 设置 `app_permission_mic_<包名>` 管控**（`0` 授权 / `-1` 拒绝）。
  「Almost/Already Expiration」说明它还有**权限有效期**机制（可能定期回收）。

### `TsMicphoneService`（`com.audio.MicphoneService`，1029 类）
- 这是 **ThunderSoft（雷石）的 USB/KTV 麦克风服务**，不是车机通话麦克风：
  `com.audio.usbmic.*`（`UsbAudioRecordLoopDriver` / `UsbAudioTrackLoopDriver` / `AudioSubMixRecorder` /
  `UsbMicDevice`）、`com.micphone.service.MicphoneService` / `MicphoneDeviceImpl` / `IEffectLoader` /
  `OnlineConfigDownloader`、`com.thunderstone.nativemicrophone`。
- 提供 `android.micphone.IMicphoneService` / `IMicphoneNotificationCallback`。
- **不解决 DiPlay 录到静音的问题**；车机通话麦克风走标准 AudioRecord（源限定 `VOICE_COMMUNICATION`，见兼容记录第八节）。

### 麦克风资源策略（ECARX）
- `com.ecarx.xui.adaptapi.policy.IMicResourceCallback` + `Policy.getAudioPolicy()` / `getVoiceAssistantPolicy()`：
  语音助手对麦克风的占用策略。可作为「为什么开麦失败」的诊断通道（待实测）。

- 实测已有：`IInputManager.registerListener(listener, packageName, keyCodes)` 无权限校验，任何 App 可订阅
  （DiPlay 的 `GeelyWheelKeys` 正是这么做的）。
- `InterceptReleaseKeyCodeUtil` + `KeyPolicyImpl`：**按键拦截**由策略实现，
  与文档结论「`interceptKeyCode` 只对 HOME(3/200003) 生效」一致。

同包还**内嵌了整个 `com.geely.os.*`（OneOS API 实现）**：`account`、`audio.GlyAudio`、`bt.GlyBt*`、
`car.GlyCar/GlyCarPropertyIds`、**`diminteraction.GlyDimInteraction` + `ActionType/DimTheme/DimMenuTab/...`**、
`input`、`wlan`、`setting` 等 —— 这是 OneOS API 的权威实现来源。

### ECARX 硬按键（第二条通道）
见 [`02`](02-框架与VDBus.md)：
- `ecarx.car.ECarXCarHardKeyManager.requestHardKeyEvent(int[], IKeyEventListener, int cookie)`；
  只接受 `ECARX_HARDKEY_MAP` 内的键码，cookie 由 `get3rdAppCookie(packageName)` 获取（`COOKIE_3rdAPP`）。
- `com.ecarx.xui.adaptapi.input.Input.requestKeysInterception(int[], IKeyCallback)` →
  内部转调上面的 `requestHardKeyEvent`；`InputImpl` 里若 `mCookie == -1` 会打印
  `unsupport client request key interception`（`evidence/method/input.InputImpl_requestKeysInterception.json`）。
  → **能否拦截取决于能否拿到有效 cookie**（第三方可能拿不到，需实测）。

## 五、权限模型（系统侧）

`system/permissions/` 21 个 XML：
- `privapp-permissions-ecarx.xml`：给 `com.ecarx.*` 授系统级权限（`INSTALL_PACKAGES`/`WRITE_SECURE_SETTINGS`/
  `CHANGE_COMPONENT_ENABLED_STATE`/`READ_LOGS`/`CHANGE_OVERLAY_PACKAGES`…）。
- `privapp-permissions-platform.xml` / `privapp-permissions-qti.xml`：AOSP/QTI 白名单。
- `platform.xml`：平台签名权限（含 `READ_LOGS`、`WRITE_SECURE_SETTINGS`、`ACCESS_SURFACE_FLINGER`…）。
- `desaysv_platform.xml`：只定义 `WRITE_MEDIA_STORAGE`（`media_rw`/`sdcard_rw`）。

车厂私有权限（`uses-permission`）需从各 APK manifest 提取；已知：
- `geely.oneos.permission.SERVICE`（`com.geely.dimservice` 声明，normal，但绑不上）。
- `com.geely.appstore.APPSTORE_PROVIDER`（normal，桌面白名单用）。
- 麦克风 `app_permission_mic_<pkg>`（secure setting，非 permission）。

> 待补：把所有 APK 的 `<permission>`/`<uses-permission>` 汇总成一张表（用 `aapt2 dump badging` + manifest）。

## 六、给 DiPlay 的可执行建议

1. **音频**：维持现方案（缓冲音乐 TCP / 车机蓝牙）；把 `VDSound*FocusStatus`、`IAudioPolicy` 纳入诊断报告。
2. **麦克风**：`app_permission_mic_*` 仍是最直接的授权方式；可尝试用 `Policy.getPermissionPolicy()` 作只读探测。
3. **方向盘键**：保留 `IInputManager` 方案；把 `ECarXCarHardKeyManager.requestHardKeyEvent` 作为
   「能否拦截麦克风键」的备选实验（先测 `get3rdAppCookie` 返回）。
4. **诊断**：`AudioExtService` 的失败日志 tag（`com.autolink.audioextservice`）与 `vdb.SomeIPUtils` 可加入抓取清单。
