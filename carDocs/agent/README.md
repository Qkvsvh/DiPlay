# AI 协作状态持久化机制

> 本目录是 DiPlay **lynk 分支**的 AI 协作交接中枢。任何 AI（或人）接手时，**先读本文件**，
> 按下面的流程恢复上下文，再动任何代码。
>
> 机制目标：遇到**网络波动、上下文异常、停电、更换 AI 模型**等中断后，
> 接手者只靠阅读本目录文档，即可全面了解项目全貌与交付状态，无缝继续工作。

---

## 一、文件清单与职责

| 文件 | 职责 | 更新时机 |
|---|---|---|
| [`README.md`](README.md)（本文件） | 机制说明 + 接手流程 | 机制变更时 |
| [`项目全貌.md`](项目全貌.md) | 项目是什么、架构、lynk 全部改动、车机适配结论、死路清单、构建命令 | 架构/适配结论变化时 |
| [`交付状态.md`](交付状态.md) | **当前做到哪了**：已完成、进行中、下一步、风险 | **每个工作段结束必更** |
| [`会话日志.md`](会话日志.md) | append-only 台账：每次工作段一条 | **每个工作段结束必追加** |

阅读顺序就是上表顺序。`项目全貌.md` 回答"这是个什么项目"，`交付状态.md` 回答"现在干到哪了"。

---

## 二、接手流程（新会话必做）

1. **确认环境**（10 秒）：`pwd` 与 `git -C DiPlay log --oneline -3`——确认工作区位置、分支（应为 `lynk`）与最新提交，和 [`交付状态.md`](交付状态.md) 顶部记录的环境快照比对；不一致（如被他人推进）时先 `git log` 摸清新变化再继续。
2. **读 [`交付状态.md`](交付状态.md)**（30 秒）：看顶部"一句话状态"判断局面；若标明"有进行中的工作"，从中断点继续，不要重做已完成的部分。
3. **读 [`项目全貌.md`](项目全貌.md)**（5 分钟）：建立完整背景。已熟悉的可跳读相关章节。
4. **按需深读**：具体问题去查 `项目全貌.md` 末尾的"文档地图"，指向 `carDocs/` 下的一手调研文档（含证据与复现命令）。
5. **继续工作前**，在 `交付状态.md` 的"进行中"登记你要做的事；完成后立即走下面的收尾规则。

---

## 三、更新规则（硬性要求）

每个工作段（一次连续的工作，无论是否被中断）收尾时**必须**：

1. **更新 [`交付状态.md`](交付状态.md)**：
   - 刷新顶部"最后更新时间 + 一句话状态"；
   - 把做完的事从"进行中"移到"已完成"；新风险记入"风险与未决"。
2. **追加 [`会话日志.md`](会话日志.md)**：一条记录，含日期、做了什么、产出/提交号、关键决策及理由。只追加，不改旧记录。
3. **大结论进 [`项目全貌.md`](项目全貌.md)**：若本段产生了永久性结论（新踩的坑、新的可用/死路通道、架构变化），同步写进对应章节，并在"死路清单"里登记重复踩坑的代价。
4. **git 提交**：文档与代码一起 commit（文档可以单独先提）。提交信息用英文一行式（跟随仓库现有风格）。
5. **证据优先**：写入文档的结论必须来自实测/反编译/可复现命令；推测要显式标注"（推测，待实测）"。

中断恢复原则：宁可文档暂时啰嗦，不可让接手者重新考古。写状态时假设"下一个读者对你本轮工作一无所知"。

## 四、本分支特有的注意事项

- 仓库根部的 [`AGENTS.md`](../../AGENTS.md) 是上游的编码规范（Settings UI 结构、CI 命令等），改代码前必读。
- 本车机（吉利/领克 FX11）的 adbd 会**切断含 `install` 字样的命令**；安装 APK 用 `carDocs/install-apk.sh`。
- release 构建内嵌从车机提取的 MFi 身份，**绝不公开分发 APK**（详见 `项目全貌.md` 安全红线一节）。
- 改代码后按 `AGENTS.md` 要求跑 CI 命令验证；纯文档改动可跳过，但要在日志里注明"纯文档改动，未跑构建"。
