# 车机兼容问题记录（领克 / 吉利 geely_fx11）

> 记录在 `geely_fx11`（领克 CS11_A4，Android 11）车机上跑 CarPlay 接收端
> （xcertplay / DiPlay）时踩到的系统级兼容问题及处理。

---

## 一、缺少 `com.android.vpndialogs` 导致启动即闪退

### 现象

在 DiPlay（或 xcertplay）点「通过 USB 连接」进入 `CarPlayHostActivity` 时立即闪退：

```
java.lang.RuntimeException: Unable to start activity .../CarPlayHostActivity:
    android.content.ActivityNotFoundException:
    Unable to find explicit activity class
    {com.android.vpndialogs/com.android.vpndialogs.ConfirmDialog}
        at ...CarPlayHostActivity.requestVpnConsent(CarPlayHostActivity.kt:665)
        at ...CarPlayHostActivity.requestStartupPrerequisites(CarPlayHostActivity.kt:637)
```

### 根因

- CarPlay（有线 USB NCM 隧道、无线也）需要 `VpnService`，首次使用要调起系统
  「VPN 连接请求」授权弹窗 `com.android.vpndialogs/.ConfirmDialog`。
- 该车机**移除了 `com.android.vpndialogs`**（`pm list packages | grep vpn` 为空），
  弹窗不存在 → `ActivityNotFoundException` → 崩溃。

### 处理（不需要改代码）

用 `appops` 直接把 VPN 激活权限预授权，`VpnService.prepare()` 会返回“已授权”，
不再拉起那个不存在的弹窗：

```bash
adb shell appops set com.shihab.diplay ACTIVATE_VPN allow
# 若跑 xcertplay：
adb shell appops set com.shilapi.xcertplay ACTIVATE_VPN allow
```

检查：

```bash
adb shell appops get com.shihab.diplay ACTIVATE_VPN
# ACTIVATE_VPN: allow
```

- 该设置**会持久化**（重启后仍在）。
- 每次重装 / 清数据后需要重新执行一次。
- 更彻底的修法：应用侧在 `requestVpnConsent` 捕获 `ActivityNotFoundException`
  并提示，而不是崩溃（`appops` 已经真授权、USB 可用，所以非必需）。

## 二、车机「车载热点」对标准 API 不可见（DiPlay 车载热点模式不适配）

### 现象

- 车机设置 → 系统 → 连接 里「车载热点」显示**已连接 1 个设备**（热点确实在工作）；
- 但 DiPlay 的「车载热点」模式提示 **热点已关闭**，且读取到的 SSID 为**空字符串**
  （需要手动在“车机热点详情”里填入 SSID / 密码才能保存）。

### 根因

- 车机（吉利/领克）用的是**定制热点实现**，未通过 Android 标准
  `WifiManager` / `SoftAp` API 暴露状态与凭据。
- DiPlay 主要面向**比亚迪**，依赖比亚迪那套接口，因此在这台车上读不到。
- 属于**适配问题**，不是配置错误。

### 结论

- DiPlay 的「车载热点」模式在该车机不可用。
- 可改用：`Wi-Fi Direct`（Wi‑Fi P2P）、`现有 Wi‑Fi / 同一局域网`、`USB`
  （USB 需先按第一节预授权 `ACTIVATE_VPN`）。
- 想用标准 API 读热点状态，可手动在 DiPlay 的「车机热点详情」里填入：

  | 项 | 值（本车示例） |
  |---|---|
  | 热点名称 | `MyCar-o5g06Y` |
  | 热点密码 | `N9fv15a6rA` |

  （`在此保存不会更改车机的热点`，只是把信息通过蓝牙转给 iPhone。）

## 四、无线 CarPlay：必须打开车机 Wi-Fi 开关

### 现象

安装后点「连接手机」，DiPlay 一直提示 **「请在车机设置中打开 Wi-Fi 后再连接。」**
并周期性重试（底层文案 `Turn on Wi-Fi in the head unit's settings, then reconnect`）。

### 根因

车机 Wi-Fi 客户端开关当时**确实关着**，DiPlay 的提示是准确的，不是误报：

```bash
adb shell cmd wifi status        # Wifi is disabled
adb shell settings get global wifi_on   # 0
```

DiPlay 的 Wi-Fi Direct 建组依赖 Wi-Fi 打开，preflight 会先检查：

```
Wi-Fi P2P preflight wifiEnabled=false locationEnabled=true permissionGranted=true ...
```

### 处理

先在车机设置里打开 Wi-Fi（设置 → 连接）。找不到开关时可临时用 adb：

```bash
adb shell cmd wifi set-wifi-enabled enabled
```

打开后 P2P 组立即建立（本车用 **5 GHz / channel 149**；channel 36 会被框架
`create rejected` 后自动回退），随后 iPhone 连上，画面/iAP2 正常。

## 五、连上后音乐只响约 1 秒就静音（实时音频流中断）

### 现象

无线连上、画面正常后，放 Apple Music 只响约 1 秒，之后一直无声；
画面、触控、iAP2 的 `NowPlayingUpdate` 与 `/feedback` 保活全部正常。

### 根因（实测）

手机先协商 **实时 RTP 音频流 `type=102`（AAC-LC 48k 立体声）**，
约 1.5 秒后 **iPhone 停止推送音频包（没有 TEARDOWN）**，DiPlay 侧缓冲耗尽：

```
15:39:02  SETUP type=102 media -> accepted
15:39:02  开始收包、解码、写 AudioTrack
15:39:03  audio playback started
15:39:04  最后一个音频包（总共仅 65 个 ≈ 1.4 秒）
15:39:07  rx=0  playing=false  rebuffers=1  underruns=+1  sinceRxMs 持续增大
之后      视频 / 触控 / iAP2 全部正常，只有音频不再来
```

- 不是音频焦点、音量或路由问题：焦点已拿到（`focus requested channel=MEDIA gain=1 granted=1`），
  且音频已正确路由到车机总线（`routeType=21` = `AudioDeviceInfo.TYPE_BUS`）。
- 与仓库 **issue #165「Geely head unit running Android 11：AAC 能写、音频被停止、视频继续」** 现象一致。
- 复现稳定：每次重建会话后都是「响一下就没」。

### 处理（已验证有效）

打开 **设置 → 显示与性能 → 缓冲音乐（实验性）**（应用后会重连 CarPlay）。

打开后 Apple Music 改走 **`type=103` 缓冲音频（TCP，提前约 2 分钟）**：

```
airplay SETUP stream type=103 ... clientID=com.apple.Music, isMedia=true
buffered audio stream client=com.apple.Music rate=48000 port=44591
audio playback started type=103
Buffered audio: queued 108 s, received 1685 kbit/s
audio stats ... playState=3 playing=true underruns=+0 rebuffers=0
```

连续播放正常。

### 备注

- 「缓冲音乐（实验性）」默认关闭，需要手动开启一次，持久保存。
- 走缓冲通道依赖 iPhone 的「增强缓冲」；不支持该能力的 App 仍会回落到会中断的 `type=102`。

### 本次测试机

| 项 | 值 |
|---|---|
| iPhone | `iPhone14,2`，iOS `27.0`，AirPlay `980.77.1` |
| 车机 | `geely_fx11` / `CS11_A4`，Android 11 |
| 连接 | 无线 Wi-Fi Direct，5 GHz channel 149 |

## 六、方向盘按键适配（切歌 + 麦克风键 → Siri）

### 现象

方向盘上的切歌键、麦克风键在 DiPlay 里**完全没反应**。车机日志显示这些键被系统独占：

```
VDS → AdapterSrv: vdbKeyCode=14 → geelyKeyCode=200231
com.geely.inputservice: onLongPressTriggered keyCode->200231
com.geely.hicar: HiCarService.handleWakeUpLongPressKeyEvent → startHiCarMainActivity
```

车机把方向盘键映射成**厂商私有键码**，只在自己的输入栈里分发，**不产生标准 Android `KEYCODE_MEDIA_*`、也没有广播**，
所以 DiPlay 的 MediaSession / 无障碍服务都收不到（对比：比亚迪会产生标准 KeyEvent，可用无障碍截获）。

### 可行通道（应用侧，不用改车机）

车机的输入服务 `com.geely.inputservice.InputService` 是 **exported** 的，其
`IInputManager.registerListener(listener, packageName, keyCodes)` **没有任何权限校验**，
任何 App 都能订阅指定键码（车机自己的 `KeyInputController` 也是这么收的）。DiPlay 在
`CarPlayMediaKeys.attach`（CarPlay 会话开始）时绑定并注册，会话结束 `detach` 时注销。

键码（`com.geely.lib.oneosapi.input.KeyCode`）：

| 键码 | 值 | DiPlay 行为 |
|---|---|---|
| `KEYCODE_R_MEDIA_PLAY_PAUSE` | 200085 | 播放 / 暂停 |
| `KEYCODE_R_MEDIA_NEXT` | 200087 | 下一首 |
| `KEYCODE_R_MEDIA_PREVIOUS` | 200088 | 上一首 |
| `KEYCODE_R_VOICE_ASSIST` | 200231 | 麦克风键长按 → Siri |

实现：

- AIDL 复刻自车机（事务码顺序必须一致）：
  `shared/src/main/aidl/com/geely/lib/oneosapi/input/{IInputManager,IInputListener}.aidl`
- 客户端：`common/src/main/java/com/shilapi/xcertplay/GeelyWheelKeys.kt`
  （仅 `LynkHeadUnit.detected` 生效；其它车机不受影响）
- 转发：`CarPlayMediaKeys.onExternalMediaKey(index)` / `onExternalSiriKey()`

### 麦克风键：停用 HiCar、改响应 Siri

麦克风键默认：**短按 = 车机语音助手，长按 = 唤醒 HiCar**。HiCar 自己注册了 200231 的监听并在长按时
`startHiCarMainActivity`，DiPlay **无法拦截**（`IInputManager.interceptKeyCode` 在车机实现里只对
HOME 键 `3/200003` 生效）。所以**直接停用 HiCar 应用**：

```bash
# 停用（持久化，重启仍生效）
adb shell pm disable-user --user 0 com.geely.hicar

# 校验：enabled=3 (DISABLED_USER)、stopped=true
adb shell dumpsys package com.geely.hicar | grep -E "enabled=|stopped="

# 需要恢复时
adb shell pm enable com.geely.hicar
```

停用后，长按麦克风键由 DiPlay 接住并调用 CarPlay 的 `requestSiri()`（`CarPlayController.requestSiri`）。

### 注意事项

- HiCar 停用是**系统层设置**，不是 App 内开关；`pm disable-user` 对系统应用在 shell 下可直接执行
  （该命令不含 `install` 关键字，不受本车 adbd 关键字过滤影响）。系统 OTA 后可能需要重跑。
- 短按仍是**车机自带语音助手**（无法从应用侧拦截），DiPlay 只接管长按 → Siri。
- 若同时有原生音乐在播，方向盘切歌会同时被车机原生链路处理（车机只按「当前音频源」路由），
  属于该车机的固有行为。

## 七、Wi-Fi 开关与热点的关系 / 持久化

### 关系

这台车**单个 Wi-Fi 芯片同时只能跑一种模式**：打开 **Wi-Fi 客户端开关**（无线 CarPlay / Wi-Fi Direct 需要）
会**关闭「车载热点」**，反之亦然。这是硬件/固件限制，不是配置错误。

因此无线 CarPlay（Wi-Fi Direct）与车机热点**不能同时开**。DiPlay 用无线时选 Wi-Fi 客户端即可，
车机热点给别的设备用就二选一。

### 打开 Wi-Fi 的方式

| 方式 | 说明 |
|---|---|
| 车机设置 → 连接 → Wi-Fi | 手动，最稳 |
| `adb shell cmd wifi set-wifi-enabled enabled` | 等价于上面，写入 `settings global wifi_on` |
| DiPlay 启动时 | `lynk` 分支已内置：无线建组前若读到 Wi-Fi 关闭，会调本机 adbd 执行上面命令（见 `LynkHeadUnit.ensureWifiEnabled`） |

> 注意：普通 App **无法**通过 `WifiManager.setWifiEnabled` 开关 Wi-Fi（Android 10+ 仅系统/运营商 App 可用）。
> 车机内部的 `com.geely.os.wlan.GlyWlanHandlerImpl.setWlanOnOff()` 最终也是调 `WifiManager.setWifiEnabled`，
> 但它跑在系统进程、且要厂商框架，第三方 App 用不了。所以应用侧唯一可行的是**本机 adbd**。

### 持久化

- `cmd wifi set-wifi-enabled enabled` 会把状态写进 `settings global wifi_on`，Android 正常**重启后会恢复**该状态。
  理论上重启一次不需要手动再开。
- 但这台车的厂商层可能在开机/使用热点时**重新接管** Wi-Fi 状态（把 `wifi_on` 置回 0）。需要实机重启验证：
  ```bash
  adb shell cmd wifi set-wifi-enabled enabled
  adb shell settings get global wifi_on      # 1
  # 重启车机后再查一次；若变 0，说明被厂商层覆盖
  ```
- 若被覆盖，可选方案：
  1. **保持本机 adbd 在线**，让 `lynk` 分支在每次无线建组前自动打开：
     ```bash
     adb tcpip 5555   # 需先 USB 连接；重启后失效，需重跑
     ```
     DiPlay 的 `LynkHeadUnit` 通过 `127.0.0.1:5555` 执行 `cmd wifi set-wifi-enabled enabled`，
     无权限弹窗；adbd 不在线时静默跳过。
  2. 找车机设置里是否有「开机保持 Wi-Fi / Wi-Fi 优先于热点」选项。
  3. 有 root 的话可用 `persist.adb.tcp.port=5555` 让 adbd 常驻 TCP，配合方案 1 自动开 Wi-Fi。

### 实测结论（本车，2026-10-07）

- **本机 adbd 不吃 TCP**：`persist.adb.tcp.port` 与 `service.adb.tcp.port` 都设成 `5555`，
  但 `/proc/net/tcp` 里没有 `:15B3` 监听，`LynkHeadUnit` 的「本机 adb 自动开 Wi-Fi」始终失败。
  **所以不要依赖 adb 方案**。
- **真正的原因**：车机开机把「车载热点」当默认打开，热点一在，Wi-Fi 客户端就被顶掉。
- **解决办法（已验证）**：在车机 **设置 → 系统 → 连接** 里**关掉「车载热点」**，再把 Wi-Fi 打开一次。
  - 强制重启车机后 `adb shell settings get global wifi_on` **仍为 1**，Wi-Fi 保持住了。
  - 结论：**不需要 adb**，只要把「车载热点」保持关闭，Wi-Fi 状态就能跨重启保持，DiPlay 直接可用。

## 八、麦克风 / 按键唤醒 Siri

### 现象

- 长按方向盘麦克风键：Siri **能被唤起**（`requestSiri` 生效），但**说话没反应、Siri 图标不动**。
- 「嘿 Siri」正常——因为它用的是 **iPhone 自己的麦克风**（日志里只有流的 SETUP，没有 App 的 `Microphone: start`）。

### 根因

车机对第三方 App 的麦克风有两道限制：

1. **车机自有权限服务** `com.desaysv.permission.service` 用 `secure` 设置
   `app_permission_mic_<包名>` 管控：`0`=授权、`-1`=拒绝（默认）。
   DiPlay 默认被拒 → `AudioRecord` 读到全 0，编码成 Opus **DTX 静音帧**（`bytes=3 head=f8fffe`）。
2. 车机只对 **`VOICE_COMMUNICATION`** 录音源真正开麦；`VOICE_RECOGNITION` 给的是静音
   （通话走 `VOICE_COMMUNICATION`，日志里能抓到 483KB 真实音频）。

### 处理

```bash
# 1) 授车机麦克风权限（0 = 授权，对齐已授权的车机语音助手 baidu）
adb shell settings put secure app_permission_mic_com.shihab.diplay 0
```

2) 本分支把 Siri（`speechrecognition`）的录音源改为 `VOICE_COMMUNICATION`
   （仅 `LynkHeadUnit.detected` 生效），见 `shared/.../media/MicrophoneUplink.kt`。

### 验证

按键 Siri 的 `Microphone: stats` 从「几乎全是 DTX 静音帧」变为**大量有效帧**
（`captureBytes=270336`、`emptyEncodedFrames=48/139`），Siri 能听到并正常响应。

> 注：`MicrophoneCaptureStats` 里 `source` 那栏是按 audioType 硬编码的标签（一直显示
> `VOICE_RECOGNITION`），不代表实际 `AudioRecord` 源，别被它误导。

## 九、实时音频（关缓冲的媒体 / 导航 / 通话）约 2 秒后停

### 现象

- 关闭「缓冲音乐」后放音乐：响约 1.5–2 秒就停；导航、通话同样（常常显示在播放但没声音）。
- 开「缓冲音乐」时音乐正常（Apple Music 走 TCP 缓冲流 `type=103`）。

### 实测（合并官方 v0.2.14 后，同一台 iPhone）

| 音乐缓冲设置 | 结果 |
|---|---|
| 2000 ms | `trackBufferFrames=105600`、`playbackHeadFrames=0` —— 预缓冲达不到 → 轨道**根本不启动** → 完全无声 |
| 300 ms | 轨道启动，播放约 1.9 秒后 `rebuffers=1` 停止 |
| 1000 ms | 写了约 1 秒，`playbackHeadFrames=0`（车机输出没消耗） |
| 2.4 GHz 信道 6 / 5 GHz 信道 149 | **都一样**，约 2 秒后停 |

- 接收侧：`Receive: audio type=102 packets=91 windowMs=51697`（51 秒里只收到约 2 秒音频），`interArrivalMaxMs≈400`。
- 与官方未解决 issue **#131**（Wi-Fi Direct 实时音频丢包/卡顿）同类。

### 结论

- 实时音频流（`type=100/101/102`）在这台车 + 该 iPhone 组合下**约 2 秒后 iPhone 不再推包**，与频段、缓冲大小都无关；
  音乐之所以稳，是因为「缓冲音乐」走 TCP。
- 「音乐缓冲」设大（1000/2000）反而因预缓冲达不到而**更没声**；本车默认已改为 **500 ms**（小值）。
- 导航/通话没有缓冲模式，暂时无法在这台车上稳定。

### 解决：改用「车机蓝牙」播放 CarPlay 音频（本车默认）

DiPlay 有个实验特性 **「通过车辆蓝牙播放 CarPlay 音频（实验性）」**（`loadCarBluetoothAudio`，官方 #432）。
打开后：

- DiPlay **不再向 iPhone 提供 CarPlay 音频输出**（`disableAudioOutput = true`）；
- 于是**音乐 / 导航 / 通话都走 iPhone ↔ 车机的蓝牙（A2DP/HFP）**，车机当蓝牙音源播放；
- 正好**绕开**上面「CarPlay 实时音频流约 2 秒就停」的问题。

实测有效（车机 A2DP Sink 已与 iPhone 连接）。**本分支已把该选项设为默认开启**（仅 `LynkHeadUnit.detected` 生效）。

使用要点：
- 车机音源要选 **蓝牙**；
- iPhone 保持与车机蓝牙配对；
- 若声音改从 iPhone 自己出，说明车机音源没切到蓝牙，把该选项关掉即可。
